# Nuclear Option 简体中文汉化补丁

Nuclear Option 的非官方简体中文本地化插件。基于 BepInEx 5，在**运行期**把界面文本替换为  
中文，不修改任何游戏文件，删除插件目录即完全还原。

**当前适配游戏版本：0.34.2**（游戏更新后词表可能部分失效，见下文「目前可能的问题」）。

词表 **4779 条**（普通 4595 ／ 整段模板 127 ／ 拼接片段 57），覆盖座舱 HUD、任务编辑器、  
设置菜单、教程弹窗、机场与航路点名称、载具与武器描述、击杀战报与聊天信息等。  
词表中还包含**一部分作者自己游玩的第三方 mod** 的装备与单位翻译 —— 原版玩家用不到这些  
词条，它们只是安静地躺在表里，没有任何副作用。

> **非官方**。本插件由玩家社区维护，与 Nuclear Option 的开发者无关；  
> 游戏内容与原文版权归其开发商所有。

## 翻译质量声明（请务必读）

**目前所有译文均由 AI 翻译，作者正在实际游玩中逐批校对和修正。**

这意味着：

- 大部分文本能看懂，但**措辞可能生硬、术语可能不统一、个别句子可能翻错**；
- 译名口径（型号 + 汉化代号、缩写保持英文等）在逐步统一，前后批次可能有差异；
- 游戏更新会改动原文措辞，导致一部分词条**静默失效**（表现为个别句子仍是英文）。

**欢迎反馈**：在游戏中按 `F11` 打开诊断窗口，「最近漏译」列表 + 插件目录下的  
`missing.json`（片段）与 `untranslated.json`（整段）就是漏翻工作清单；提交 issue 时  
附上这两份文件（或截图）最有效。词表是纯 JSON，也直接接受译文 PR。

### 目前可能的问题

按出现概率排列：

1. **个别句子仍是英文** —— 游戏更新改了原文，或该文本走了未覆盖的通路。  
   这是常态，逐批修。
2. **译文措辞生硬或术语不统一** —— AI 翻译的历史遗留，实机游玩中逐步替换。
3. **极少数界面文本长度变化导致的显示溢出** —— 中文通常比英文短，但个别标签  
   （座舱 HUD 的 2 字槽位）译文过长会显示不全，发现一个修一个。
4. **第一次显示某个新汉字时轻微卡顿** —— 字体图集现场栅格化，一次性开销，之后不再发生。
5. **游戏更新后插件可能整体失效** —— 补丁目标方法被改名/移除时，对应补丁装不上  
   （日志里会报「补丁 xxx 安装失败」），需要等适配。

## 特性

- **纯运行期替换** —— 不修改游戏资源与存档，不触发文件完整性校验。
- **词表热重载** —— 改完词表在设置窗口点一下即可生效，不必重启游戏。
- **数据与代码分离** —— 词表是可读的 JSON，人人都能做贡献。
- **分层翻译流水线** —— 能整体翻就整体翻，不行就切分、剥标签、只翻主干再拼回变量。  
  富文本、动态读数、拼接战报都能处理（见 [`docs/ARCHITECTURE.md`](docs/ARCHITECTURE.md)）。
- **自带中文字体回退** —— 运行期把 `font.ttf` 造成 TMP 字体资产并登记进回退链，  
  不需要手改游戏的字体资产。
- **自带诊断窗口** —— `F11` 呼出，能当场看出"哪条文本命中了、哪条漏掉了"，  
  不必翻日志。

## 安装

1. 安装 [BepInEx 5](https://github.com/BepInEx/BepInEx/releases)（**x64**）到游戏根目录，  
   先启动一次游戏以生成 `BepInEx/plugins/`。
2. 把本插件的目录整个放进 `BepInEx/plugins/`：
   ```
   <游戏>/BepInEx/plugins/NuclearOptionChineseLocalizationPatch/
   ├─ NuclearOptionChineseLocalizationPatch.dll    插件本体
   ├─ Newtonsoft.Json.dll                          JSON 解析依赖（必须一起放）
   ├─ translation.json                             词表（唯一事实来源）
   ├─ exclusions.json                              不翻译名单
   ├─ force_scopes.json                            强制作用域名单
   ├─ font.ttf                                     中文字体（约 10 MB）
   └─ scopes/                                      分作用域词表
      └─ TypeText.json
   ```
3. 启动游戏。启动后 `BepInEx/LogOutput.log` 里应出现：
   ```
   Nuclear Option Chinese Localization Patch v1.5.2 已启动。
   词表已载入：普通 4595 / 模板 127 / 片段 57 / 作用域 …
   [自检] Harmony 生效 = True
   ```
   这三行同时说明「版本正确」「词表读到了」「补丁真的装上了」。

> ⚠️ **不要与其他汉化插件同时启用。** 多个插件会同时挂钩同一个文本组件，行为无法预测。  
> 安装前请先移除旧的中文插件目录。

> ⚠️ **必须重启游戏，而不是重载词表。** 插件本体（DLL）只在启动时加载；  
> 重载只重读 JSON 数据。

## 使用

按 `F11` 呼出「设置与诊断」窗口（纯 IMGUI，不依赖任何额外资源）：

| 区块 | 内容                                                    |
| -- | ----------------------------------------------------- |
| 操作 | 开关翻译（关闭会把屏上中文还原成英文）／重新载入词表／立即扫描场景／清空缓存／清空漏译记录         |
| 状态 | 逐帧宿主是否就绪、词表与排除名单条数、最近一次载入结果、场景与扫描次数、命中/漏译/缓存统计、防回写跟踪数 |
| 调节 | 兜底扫描开关（**默认关**）与间隔、是否记录最近命中、是否累积漏译、是否输出调试日志  |
| 诊断 | **最近命中**（原文 → 译文）与**最近漏译**（`<作用域>片段`）各 12 条           |

诊断区是排查"某处为什么没翻"最快的手段：一条文本要么出现在命中列表里（说明流水线跑到了、  
只是结果不对），要么出现在漏译列表里（说明词表缺条目），要么**两边都没有**——  
那说明它根本没进流水线（补丁没覆盖到那条通路）。

## 配置

首次启动后生成 `BepInEx/config/com.nuclearoption.zhcn.localization.cfg`。  
**配置只在启动时读取**，热重载词表不会重读配置。

| 分区          | 项                       | 默认      | 说明                                             |
| ----------- | ----------------------- | ------- | ---------------------------------------------- |
| General     | `Enabled`               | `true`  | 关闭后会把屏上已有的中文还原成原文                              |
| General     | `ToggleWindowHotkey`    | `F11`   | 呼出设置窗口的热键                                      |
| General     | `ReloadDataHotkey`      | 空       | 不打开窗口、直接热重载词表的热键。留空表示只用窗口按钮                    |
| Diagnostics | `VerboseLogging`        | `false` | 调试级日志。翻译在渲染路径上被高频调用，仅排障时开                      |
| Diagnostics | `LogMisses`             | `true`  | 把未翻译文本累积到 `missing.json` / `untranslated.json` |
| Performance | `ScanIntervalSeconds`   | `0`     | 兜底扫描间隔（秒）。`0` = **关闭兜底扫描**（默认）；> 0 时作为窗口滑块的初值   |
| Performance | `TranslationCacheLimit` | `20000` | 翻译结果缓存条目上限。`0` 表示禁用缓存（不推荐）                     |

## 性能影响

### 结论先说

在正常规模下开销**很小，但不是零**。三处需要注意：

1. **显存**：中文字体图集是主要占用，估算 **24–40 MB**（见下）。
2. **每次文本赋值**都会走一遍流水线 —— 已缓存的文本成本是"几次字典查询 + 一次字符扫描"级别，  
   但每次都会产生少量字符串分配（GC 压力）。
3. **兜底扫描**（**默认关闭**）会分配数组并遍历场景中所有文本组件，是**可调节**的主要周期开销。

默认配置下第 3 项不存在；如果你打开了兜底扫描并在弱 CPU 上感到掉帧，  
把 `ScanIntervalSeconds` 调大（或在窗口里拉滑块）。

### 成本模型

**① 每次文本赋值（热路径，最高频）**

补丁挂在 `TMP_Text.text` setter / `SetText(string,bool)` / `SetText(StringBuilder)` /  
`ParseInputText` / `OnEnable` 上，每次赋值都会经过流水线。经过的关卡与代价：

| 关卡       | 代价                                                               |
| -------- | ---------------------------------------------------------------- |
| 宿主看门狗    | 一次 Unity 原生指针比较，宿主已就绪时 O(1)                                      |
| 作用域推断    | 读一次 `gameObject.name` —— **原生调用，每次都分配一个新的托管字符串**，这是每次调用里最固定的那笔开销 |
| 排除名单     | 2 次哈希查询；`texts`(36) 与 `terms`(26) 的形态判定是**线性扫描**加前缀比较            |
| 模板门禁     | 先按最短键长做长度判定；通过后做一次正则归一化（标签替换 + 空白折叠），**这是最贵的一步**，但对短文本很快         |
| 中文短路     | O(n) 字符扫描。**已翻过的文本在这里就返回了**，这是最有效的一道闸                            |
| ASCII 判定 | O(n) 字符扫描。HUD 上大量纯数值读数在这里返回，不进后续正则                               |
| 缓存查询     | 一次字典查询（默认上限 20000 条，满了整体清空）                                      |

⇒ 稳态下绝大多数调用命中的是"缓存查询"或"中文短路"，成本很低；  
只有**第一次**遇到某条文本才会走完整套切分/片段匹配/正则。

**② 兜底扫描（默认关闭）**

`Resources.FindObjectsOfTypeAll<TMP_Text>()` + `FindObjectsOfTypeAll<UI.Text>()`，  
对每个组件做一次原地翻译。它负责补丁覆盖不到的两类文本（预制体自带默认值、  
绕过 setter 直接写字段）。

**默认关闭**，原因：这个 API 枚举的是场景 + 所有已加载资产，单次几毫秒到几十毫秒，  
还伴随数组分配的 GC 压力 —— 不是每个玩家都愿意为"少数补丁覆盖不到的文本"  
常年在后台付这笔钱。

- **场景加载时仍必定扫一次**（不受开关影响），保证每关开始时界面是完整的。
- 需要运行期持续补翻时，在 F11 窗口里勾选「兜底扫描」实时开启；间隔 0.1–5 秒实时调节。
- 打开后有两层自动节流：界面稳定时间隔自动放慢（最长 8 倍）、拖动视角时暂停。
- 翻译主体不依赖它：绝大多数文本走的是补丁路径（setter / OnEnable 挂钩），  
  关闭扫描只影响"极少数一直保持英文的文本"，不影响已翻译内容的正确性。

**③ 每帧一次的防回写补偿**

`LateUpdate` 里遍历已跟踪的组件（上限 4000），逐个读字段并比较字符串。  
只对**成功翻译过的**组件记账，所以空场景下几乎是零。

- 若某个组件被游戏每帧覆盖，补回次数在 1 秒内超过 5 次就**主动放弃**它（宁可显示英文，  
  也不让每帧读写拖垮帧率）。放弃数量在窗口「防回写」一行可见。

**④ 显存与内存**

| 项      | 量级                                                                                                                  |
| ------ | ------------------------------------------------------------------------------------------------------------------- |
| 字体图集   | 2048×2048 SDF 单通道 ≈ **4 MB / 张**。按 90px 采样 + 9px 边距，单张约容 350 个字形；常用汉字 2000–3500 个 ⇒ 预计 6–10 张 ⇒ **约 24–40 MB**（估算值） |
| 词表     | `translation.json` 368 KB → 载入后的字典 + 反向索引，托管字符串量级为**几 MB**                                                          |
| 翻译缓存   | 上限 20000 条（`TranslationCacheLimit`）                                                                                 |
| 译文→原文表 | 上限 8192 条，满时整体清空                                                                                                    |

> 图集为什么要开这么大：TMP 默认 1024×1024 只装得下约一百个 90px 字形，图集放满后  
> TMP 会重建并重新上传整张纹理，表现就是周期性卡顿掉帧。开到 2048×2048 并允许多图集后，  
> 常用字基本能一次性装下。代价就是上面这几张纹理的显存。
>
> 另有一笔**一次性**开销：某个汉字第一次被显示时，TMP 要现场栅格化字形并上传到图集。  
> 表现为"第一次打开某个界面时轻微卡一下"，之后不再发生。

**⑤ 磁盘 I/O**

- 漏译记录节流 30 秒才落盘一次，且写盘失败静默忽略 —— 诊断功能不允许影响游戏。
- 调试日志默认为**关**，因为翻译路径被高频调用，逐条写盘会明显拖慢。

### 我们**没有**做的事

诚实地说清楚边界：

- **没有做过帧时间实测。** 上面的结论来自代码路径与数据结构分析，不是 benchmark。  
  如果你需要确切数字，用下面的方法自己量。
- 没有做多线程、没有做批处理合并、没有对正则做缓存池。如果实测下来有热点，  
  这些是下一步该动的地方（尤其"作用域推断每次都分配字符串"这一条）。

### 自己怎么量

1. 打开 `F11` 窗口，看「运行统计」的 **命中 / 漏译 / 缓存 / 放过** 四个数。  
   `缓存` 长期贴近上限时说明场景文本种类很多，可考虑调大 `TranslationCacheLimit`。
2. 兜底扫描默认关闭，平时不构成开销；若你打开了它，可拉到 **5 秒**对比帧率，  
   无明显改善 → 瓶颈不在这里。
3. `VerboseLogging` 只在排障时打开，量完记得关。
4. 想临时完全排除本插件：窗口里点「关闭翻译（还原英文）」，或直接把 `Enabled` 改为 `false`  
   重启 —— 前者会停止翻译并还原显示，但插件仍在运行。

## 多人游戏风险

**再次强调：本插件仅在单人游戏下验证过。多人游戏请自担风险，并且建议不要用。**

按"风险从确定到不确定"排列：

### 1. 未做多人测试（确定）

所有验证都在单人环境下完成。**未测试不等于已证明安全** —— 下面几条是我们在代码层面  
能识别的隐患，但联机路径上的行为没有任何实测覆盖。

### 2. 本插件会改写游戏"读回"的文本（最主要的隐患）

游戏里大量存在「读出来比较、不一样就写回去」的写法，例如  
`if (weaponName.text != info.shortName) weaponName.text = info.shortName;`。  
只要读出来是中文，比较就恒为真，游戏就会每帧把英文重写一遍 —— 表现为右上角文本  
"闪一下中文又变回英文"。

为此，本插件把 **TMP 的 `text` getter 改成返回英文原文**  
（`PatchHelpers.RestoreOriginalOnRead`）。TMP 的渲染走 `m_text` 字段而不经过 getter，  
所以屏上显示的仍是中文。

**但这意味着：任何"读取界面文本再拿去比较 / 查找 / 发送"的逻辑，读到的是被我们改过的  
那一份。** 在单人游戏里这已被验证是安全的；在联机路径上我们无法保证 —— 这就是  
"不可预见"的主要来源。旧版 `UI.Text` 刻意没有做这个改写（它的文本网格直接读 `text`，  
改读回值会连显示一起变成英文）。

### 3. 注入式 DLL 与服务器规则（确定存在，但取决于服务器）

本插件通过 BepInEx 在内存中改写游戏方法。部分服务器 —— 尤其竞技 / 排位性质的 ——  
把"客户端注入 DLL"视为作弊或违规，也可能启用客户端完整性校验。

- **在要求客户端为原版的服务器上不要使用。**
- 也不要指望"别人也用同一个汉化"就能豁免：这是服务器运营方的判定，不是本插件的判定。

### 4. 原生界面的逻辑一致性（不确定）

原生界面（服务器大厅、装备选择、指令菜单）的文本被翻译后，如果有本地逻辑依赖某个  
字符串常量做匹配，可能匹配失败。单人下已验证的路径**不覆盖多人专有界面**。

### 5. 帧时间（不确定）

多人场景里实体与文本组件更多，兜底扫描与防回写的遍历对象也更多（见[性能影响](#性能影响)）。  
弱 CPU 上可能出现掉帧，而掉帧在对局中的代价比在单人里高。

### 6. 不做兼容性承诺（确定）

游戏更新、其他 mod、服务器魔改都可能与本插件冲突。冲突的表现更可能是**联机对局中偶发异常**，  
而不是干脆崩溃 —— 这种问题最难归因，也最难支持。

### 补充：本插件的设计边界

有两处是**有意**做成这样、并且对降低风险有帮助的，值得一提：

- **不做任何网络写入。** 所有补丁只作用于文本组件；翻译结果不会进网络消息。  
  例如击杀战报那条通路（`MessageFeed.RefreshUI`）拼串用的是调用方自己的  
  `StringBuilder`，本插件是**换引用**而不是就地改写，所以调用方对象里的内容  
  仍是原文。
- **只写回含中文的结果。** 若把一种英文写成另一种英文，会形成 A→B→A 的来回改写、  
  文本每帧重建。这条收敛性限制同时挡住了大量潜在的抖动。

**建议**：只在单人局使用；与他人联机前先移除插件目录；若确实要在多人下试，  
优先在**自建服务器**上验证，并预期可能需要自行排查问题。

## 从源码构建

需要 .NET SDK。`GameDir`（游戏根目录）的解析链会自动适配，仓库放在  
`<游戏>/Git/<本仓库>` 时**零配置**即可构建：

```bash
dotnet build -c Release                 # 编译并部署 DLL
dotnet build -c Release -t:Rebuild      # 强制全量重编译
dotnet build -c Release -t:DeployData   # 全量同步数据文件到插件目录
```

游戏不在默认位置时，任选一种方式指定：

```bash
dotnet build -c Release -p:GameDir="D:\Games\Nuclear Option"
# 或设置环境变量 NUCLEAR_OPTION_DIR
# 或复制 GameDir.props.example 为 GameDir.props 并填入路径
```

> ⚠️ **`-t:DeployData` 不触发编译**，它的依赖链不经过 `CoreCompile`，复制的是  
> `bin/` 里的上一次产物。改了 `.cs` 必须先 `-t:Rebuild`，再 `-t:DeployData`。

> ⚠️ **`PostBuild` 不会覆盖已有的数据文件。** 它只推 DLL，并在数据文件**不存在**时做一次  
> 首次安装引导 —— 这是为了不冲掉你在游戏里热改过的 `translation.json`。  
> 想让仓库里的数据强制覆盖运行时那份，用 `-t:DeployData`。

改完词表后跑一遍数据自检（编码、键唯一性、键序、括号规范等）：

```bash
python tools/check_data.py
```

## 数据格式

词表是扁平的 `{ "原文": "译文" }`。除普通词条外还有五类特殊键：

| 前缀        | 用途                | 例子                            |
| --------- | ----------------- | ----------------------------- |
| `[Scope]` | 限定作用域，区分同名不同义的原文  | `[KillFeed]sank`              |
| `~`       | 整段模板（教程弹窗、含标签的长句） | `~<b>Return</b>\nAlkyon AB-4` |
| `>>`      | 拼接前缀片段            | `>>Warning : `                |
| `<<`      | 拼接后缀片段            | `<< sank`                     |
| `==`      | 拼接中段片段            | `== deployed at `             |


片段键的长度与空格**都是语义的一部分**（运行时取 `Substring(2)`，不做 trim），  
写错一个空格就永不命中。完整规则（归一化顺序、片段拼接语义、数值尾模式）见  
[`docs/ARCHITECTURE.md`](docs/ARCHITECTURE.md)。

运行期还会在插件目录生成两个**诊断文件**（可以随时删，删了会自动重建）：

- `missing.json` —— 未翻译的**片段**（切片后的最小可翻译单元），补词表的工作清单。
- `untranslated.json` —— 未翻译的**整段长文本**（≥ 80 字符），因为片段清单里的截断文本  
  对不上运行时的键。

## 性能影响（完整论证）

### 成本模型

**① 每次文本赋值（热路径，最高频）**

补丁挂在 `TMP_Text.text` setter / `SetText(string,bool)` / `SetText(StringBuilder)` /
`ParseInputText` / `OnEnable` 上，每次赋值都会经过流水线。经过的关卡与代价：

| 关卡 | 代价 |
|---|---|
| 宿主看门狗 | 一次 Unity 原生指针比较，宿主已就绪时 O(1) |
| 作用域推断 | 读一次 `gameObject.name` —— **原生调用，每次都分配一个新的托管字符串**，这是每次调用里最固定的那笔开销 |
| 排除名单 | 2 次哈希查询；`texts`(64) 与 `terms`(25) 的形态判定是**线性扫描**加前缀比较 |
| 模板门禁 | 先按**最短那条模板键**做长度判定 —— 现为 **7 字符**（由 `~END {#}H{#}` 钉死；2026-09-28 清掉 9 条冗余短模板后曾是 11，之后新增短模板又降回 7）。长度 < 7 的文本在这一步直接返回、免掉下一步归一化。⚠️ **新增短模板会无声把全体文本的门槛拖回去**，`tools/check_data.py` 的「模板门禁」提示就是盯这个的 |
| 模板归一化 | 标签替换 + **空白折叠**，是热路径上最贵的一步。折叠已加无损快路径：不含 `\t`、也没有连续空格的文本直接 `Trim` 返回，不跑正则 |
| 中文短路 | O(n) 字符扫描。**已翻过的文本在这里就返回了**，这是最有效的一道闸 |
| ASCII 判定 | O(n) 字符扫描。HUD 上大量纯数值读数在这里返回，不进后续正则 |
| 缓存查询 | 一次字典查询（默认上限 20000 条，满了整体清空） |

⇒ 稳态下绝大多数调用命中的是「缓存查询」或「中文短路」，成本很低；
只有**第一次**遇到某条文本才会走完整套切分/片段匹配/正则。

**② 兜底扫描（默认关闭）**

`Resources.FindObjectsOfTypeAll<TMP_Text>()` + `FindObjectsOfTypeAll<UI.Text>()`，
对每个组件做一次原地翻译。它负责补丁覆盖不到的两类文本（预制体自带默认值、
绕过 setter 直接写字段）。

**默认关闭**，原因：这个 API 枚举的是场景 + 所有已加载资产，单次几毫秒到几十毫秒，
还伴随数组分配的 GC 压力 —— 不是每个玩家都愿意为「少数补丁覆盖不到的文本」
常年在后台付这笔钱。

- **场景加载时仍必定扫一次**（不受开关影响），保证每关开始时界面是完整的。
- 需要运行期持续补翻时，在 F11 窗口里勾选「兜底扫描」实时开启；间隔 0.1–5 秒实时调节。
- 打开后有两层自动节流：界面稳定时间隔自动放慢（最长 8 倍）、拖动视角时暂停。
- 翻译主体不依赖它：绝大多数文本走的是补丁路径（setter / OnEnable 挂钩），
  关闭扫描只影响「极少数一直保持英文的文本」，不影响已翻译内容的正确性。

**③ 每帧一次的防回写补偿**

`LateUpdate` 里遍历已跟踪的组件（上限 4000），逐个读字段并比较字符串。
只对**成功翻译过的**组件记账，所以空场景下几乎是零。

- 若某个组件被游戏每帧覆盖，补回次数在 1 秒内超过 5 次就**主动放弃**它（宁可显示英文，
  也不让每帧读写拖垮帧率）。放弃数量在窗口「防回写」一行可见。

**④ 显存与内存**

| 项 | 量级 |
|---|---|
| 字体图集 | 2048×2048 SDF 单通道 ≈ **4 MB / 张**。按 90px 采样 + 9px 边距，单张约容 350 个字形；常用汉字 2000–3500 个 ⇒ 预计 6–10 张 ⇒ **约 24–40 MB**（估算值） |
| 词表 | 9 个分类文件合计约 390 KB（其中 `translation.json` 278 KB）→ 载入后的字典 + 反向索引，托管字符串量级为**几 MB** |
| 翻译缓存 | 上限 20000 条（`TranslationCacheLimit`） |
| 译文→原文表 | 上限 8192 条，满时整体清空 |

> 图集为什么要开这么大：TMP 默认 1024×1024 只装得下约一百个 90px 字形，图集放满后
> TMP 会重建并重新上传整张纹理，表现就是周期性卡顿掉帧。开到 2048×2048 并允许多图集后，
> 常用字基本能一次性装下。代价就是上面这几张纹理的显存。
>
> 另有一笔**一次性**开销：某个汉字第一次被显示时，TMP 要现场栅格化字形并上传到图集。
> 表现为「第一次打开某个界面时轻微卡一下」，之后不再发生。

**⑤ 磁盘 I/O**

- 漏译记录**默认关闭**（配置 `LogMisses = false`）：插件分不清游戏原文与第三方文本
  （创意工坊物件名、玩家呼号等会被一并记进来），清单噪声远多于真缺口，且写盘是常驻开销。
  需要报漏翻或自己补词表时再打开。打开后也是节流 30 秒才落盘一次，写盘失败静默忽略
  —— 诊断功能不允许影响游戏。
- 调试日志默认为**关**，因为翻译路径被高频调用，逐条写盘会明显拖慢。
- 「记录最近命中」（`F11` 诊断区那 12 条）默认也**关**。它不属于磁盘开销，而是**每次命中**
  多做一遍字符串裁剪与入队；关掉只影响那份滚动列表，「累计 N 条」计数照常统计。

> 安装后的默认状态是**只开翻译**：兜底扫描、调试日志、漏译记录、最近命中、性能探针五项全关，
> 也不生成任何诊断文件。

### 实测（2026-10）：探针 + 整帧两种方法

这一版把「成本模型」落到了两组实机数据上，并补上了 2026-09 没做的那件事：**帧时间实测**。

**测量工具**是插件自带的性能探针（`F11` →「性能探针」，默认关）：它把热路径拆成五段分别计时，
统计每秒调用次数、GC 与分配量，自 2.0.1 起**每个 1 秒窗口都会落盘**成 `probe-<时间>.csv`，
配合仓库里的 `tools/analyze_probe.py` 可以出分位数与成本归因，不必再人工读屏。
另有一个仓库外的测试台（直链 `src/Core`、拿整份词表当语料）给出**流水线本身**的下限。

#### ① 探针读数（每帧本地化耗时）

| 场景 | P50 | P90 | P99 | 占帧预算 |
|---|---|---|---|---|
| 低负载平飞（自由帧率 109 fps） | **0.176 ms** | 0.225 ms | 0.286 ms | **1.93%** |
| 中高负载平飞（全面战场 60 fps） | **0.287 ms** | 0.379 ms | 0.454 ms | **1.72%** |

| 指标 | 读数 | 条件 |
|---|---|---|
| 单次赋值（流水线本身） | **约 2.5 µs** | 测试台热稳态，纯 CLR |
| 单次赋值（实机） | **7.54 µs**（低负载）/ **9.64 µs**（中高负载） | 含探针自身开销 |
| 赋值频次 | **2558 次/秒**（低负载）/ 1724（中高负载，因帧率低） | P50 |
| 每帧赋值次数 | **23.4**（低负载）/ **28.7**（中高负载） | P50 |
| 每秒 CPU 时间 | **19.3 ms** / **16.6 ms** | 折算单核 1.9% / 1.7% |
| GC0 | **4–5 次/分钟** | 采样窗口 |
| 显存 | 24–40 MB | 字体图集（估算，见上表） |

**「单次成本」为什么比 2026-09 高**：那一次的 5.5–7.3 µs 是在读数窗口最稀的场景采的。
把两档放在一起看就清楚了 —— 单次成本随 CPU 负载上升 28%（7.54 → 9.64 µs），
这是缓存压力与竞争，不是词表变大。**跨场景比较「单次 µs」没有意义，比较「每帧 ms」才有。**

#### ② 整帧实测（A/B）与它为什么失败

2026-09 的待办是「补帧时间实测」。这一版做了，结论是**这条路走不通**：

| 观测 | 数值 |
|---|---|
| 同一遍录制内、同高度巡航的 20 秒窗 P50 极差 | **1.97 ms** |
| 恒高 3500 m 巡航仍存在的「进段后变快」台阶 | **1.25 ms**（前一次 2.16 ms） |
| 待检出的汉化开销 | **0.18 ms** |

即：**工况噪声是信号的 4~11 倍**。最终用两组完整全帧数据做了配对（7 个 10 秒窗）：

- 整段平均差 −0.05 ms（汉化反而略快，纯噪声）
- 差值中位 +0.05 ms，符号检验 4 慢 : 3 快（p = 1.0）→ 无方向性
- 标准差 0.895 ms，**95% 置信区间 = [−0.93, +0.73] ms**，包含 0

**结论改写**：热路径仍不构成帧率问题（占帧预算 1.7~1.9%），但"按 60 fps 折算 0.1–0.4 ms/帧"
这种由探针推算的说法，现在有了外部校验 —— 整帧口径给出的上界是 **0.73 ms**，
与探针的 0.18 ms 相容。**两个独立方法指向同一结论：影响存在、量级很小、整帧测不出来。**

⚠️ **读这些数字时的三点注意**（别把它们当绝对基准）：

1. **测试台与实机不可直接相比。** 测试台没有 Unity、没有探针开销、语料是整份词表；
   实机读数包含探针本身约 0.4 µs/次的开销与运行环境差异。
2. **不同轮次的实机采样之间也不可比。** 条件不同（场景、赋值密度），差异更多反映「这一局在干什么」，
   而不是插件变快或变慢。
3. **`B/次` 与 `B/帧` 要分开看。** 分配量里混着「与赋值次数无关的每帧固定开销」——
   用单一的总 KB/秒去横比不同场景会得出错误结论。

**已优化过的两处**（都在「缓存之前」，也就是每次赋值都会走到的位置）：

- **空白折叠加无损快路径。** 词表 5231 条语料里只有 **6 条（0.12%）** 真的需要跑折叠正则 ——
  此前 99.9% 的文本都在做「换完与原文一字不差」的恒等替换。实测单次赋值 −26%、分配 −48%、
  Gen0 次数 −48%。
- **作用域查询里的死回落改用加载期标志位。** `translation.json` 中以 `[` 开头的键为 **0 条**，
  那条「未命中就回落去查 `_global["[scope]原文"]`」的路径永远不可能命中，
  却在每次未命中时白分配两个字符串。

### 我们**没有**做的事

诚实地说清楚边界：

- **没有做「极限刷屏」场景的整帧实测。** 实测的赋值峰值只到 3530 次/秒。按 9.64 µs/次外推，
  8000 次/秒（战报连刷 + 数据链滚动 + 僚机台词同时出现）约 1.29 ms/帧、占 60 fps 预算 7.7%；
  12000 次/秒 才到 11.6%。这只是推算，没有实测支撑。
- **中高负载那一档缺汉化侧的整帧数据。** 原版基线是干净的（82.8 s / P50 16.52 ms），
  但汉化侧那段录制没有打点、且战斗负载在 2 分钟内累积了 84%（11.2 → 20.7 ms），不是稳态，
  故未参与对比。
- **没有做多线程、没有做批处理合并、没有对正则做缓存池。** 实测下来热路径已经没有
  「值得改」的项（占帧预算 1.7~1.9%、GC 4~5 次/分钟），继续加码的收益低于引入缺陷的风险。
- **没有优化名单判定。** 它是当前最大单项（占本地化耗时的 31~35%），且每次赋值被调用约 2 次。
  若将来要把 0.18 ms 压到 0.12 ms 以下，这是唯一有意义的入口 —— 但按现在的占比，
  收益上限也只有 1 个百分点的帧预算。

### 自己怎么量

1. **开性能探针并让它落盘。** `F11` →「性能探针」，约 1 秒出数（三行：每秒调用次数 /
   各段耗时与占比 / 单次峰值与分配），**同时开始写** `<插件目录>/probe-<时间>.csv`。
   面板只留最近一秒，要看分布必须靠落盘的 CSV。**它本身有开销，量完记得关**。
2. **用脚本出结论。** `python tools/analyze_probe.py <probe-*.csv>` 给每帧本地化耗时的
   均值/P50/P90/P99、赋值频次分布、成本归因、逐 5 秒曲线。
   判读口径：**先看 ms/帧，再看 cps**；单次 µs 跨场景不可比。
3. 打开 `F11` 窗口，看「运行统计」的 **命中 / 漏译 / 缓存 / 放过** 四个数。
   `缓存` 长期贴近上限时说明场景文本种类很多，可考虑调大 `TranslationCacheLimit`。
4. 兜底扫描默认关闭，平时不构成开销；若你打开了它，可拉到 **5 秒**对比帧率，
   无明显改善 → 瓶颈不在这里。
5. `VerboseLogging` 只在排障时打开，量完记得关。
6. 想临时完全排除本插件：窗口里点「关闭翻译（还原英文）」，或直接把 `Enabled` 改为 `false`
   重启 —— 前者会停止翻译并还原显示，但插件仍在运行。

> **别用「开/关插件对比帧率」来量这个。** 整帧噪声下限是 ±0.8 ms，比要测的开销大 4 倍以上；
> 实测两组完整数据得到的 95% 置信区间跨零。用探针，不要用帧率。

## 多人游戏风险（完整论证）

**再次强调：本插件仅在单人游戏下验证过。多人游戏请自担风险，并且建议不要用。**

按「风险从确定到不确定」排列：

### 1. 未做多人测试（确定）

所有验证都在单人环境下完成。**未测试不等于已证明安全** —— 下面几条是我们在代码层面
能识别的隐患，但联机路径上的行为没有任何实测覆盖。

### 2. 本插件会改写游戏「读回」的文本（最主要的隐患）

游戏里大量存在「读出来比较、不一样就写回去」的写法，例如
`if (weaponName.text != info.shortName) weaponName.text = info.shortName;`。
只要读出来是中文，比较就恒为真，游戏就会每帧把英文重写一遍 —— 表现为右上角文本
「闪一下中文又变回英文」。

为此，本插件把 **TMP 的 `text` getter 改成返回英文原文**
（`PatchHelpers.RestoreOriginalOnRead`）。TMP 的渲染走 `m_text` 字段而不经过 getter，
所以屏上显示的仍是中文。

**但这意味着：任何「读取界面文本再拿去比较 / 查找 / 发送」的逻辑，读到的是被我们改过的
那一份。** 在单人游戏里这已被验证是安全的；在联机路径上我们无法保证 —— 这就是
「不可预见」的主要来源。旧版 `UI.Text` 刻意没有做这个改写（它的文本网格直接读 `text`，
改读回值会连显示一起变成英文）。

### 3. 注入式 DLL 与服务器规则（确定存在，但取决于服务器）

本插件通过 BepInEx 在内存中改写游戏方法。部分服务器 —— 尤其竞技 / 排位性质的 ——
把「客户端注入 DLL」视为作弊或违规，也可能启用客户端完整性校验。

- **在要求客户端为原版的服务器上不要使用。**
- 也不要指望「别人也用同一个汉化」就能豁免：这是服务器运营方的判定，不是本插件的判定。

### 4. 原生界面的逻辑一致性（不确定）

原生界面（服务器大厅、装备选择、指令菜单）的文本被翻译后，如果有本地逻辑依赖某个
字符串常量做匹配，可能匹配失败。单人下已验证的路径**不覆盖多人专有界面**。

### 5. 帧时间（已量化，风险为低）

多人场景里实体与文本组件更多，兜底扫描与防回写的遍历对象也更多（见上文「性能影响」）。
弱 CPU 上可能出现掉帧，而掉帧在对局中的代价比在单人里高。

不过 2026-10 的实测把这个风险压低了：中高负载（全面战场默认配置，60 fps 顶满）下，
翻译链路占帧预算 **1.72%**，整帧 A/B 的差异在 95% 置信区间内跨零。
真正的放大器是**文本刷新频次**（实测峰值 3530 次/秒，外推 8000 次/秒 才到 7.7%），
而多人对战里的战报、数据链、僚机台词密度可能比单人更高 —— **这是唯一尚未覆盖的工况**。
若你在实战中确实观察到掉帧，按「自己怎么量」开一次探针，看 `cps` 那一列即可判断是不是它。

### 6. 不做兼容性承诺（确定）

游戏更新、其他 mod、服务器魔改都可能与本插件冲突。冲突的表现更可能是**联机对局中偶发异常**，
而不是干脆崩溃 —— 这种问题最难归因，也最难支持。

### 补充：本插件的设计边界

有两处是**有意**做成这样、并且对降低风险有帮助的，值得一提：

- **不做任何网络写入。** 所有补丁只作用于文本组件；翻译结果不会进网络消息。
  例如击杀战报那条通路（`MessageFeed.RefreshUI`）拼串用的是调用方自己的
  `StringBuilder`，本插件是**换引用**而不是就地改写，所以调用方对象里的内容
  仍是原文。
- **只写回含中文的结果。** 若把一种英文写成另一种英文，会形成 A→B→A 的来回改写、
  文本每帧重建。这条收敛性限制同时挡住了大量潜在的抖动。
